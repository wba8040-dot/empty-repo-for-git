# 補貨檢查

> 這是**挖空模板**。標 ★ 的地方要你自己填。
> 重點是「數字一定要從盤點資料抄，不能自己編」，而且每個數字都要能驗算。

## 什麼時候用

- 跑完 `npm run simulate`，要決定下一版策略每樣菜備幾份時
- 在瀏覽器玩完一天，想看「倉庫盤點」頁的結果該怎麼調整時

## 資料從哪裡來

在 `web-lab` 資料夾執行：

```text
npm run simulate -- plans/策略檔.json --json
```

每一天的 `inventory` 欄位，是那天每樣上架的菜的盤點：

| 欄位 | 意思 | 怎麼驗算 |
|---|---|---|
| `name` | 菜名 | — |
| `stocked` | 早上備了幾份 | 策略檔裡的 `qty` |
| `sold` | 賣出幾份 | 打烊報表 |
| `waste` | 報廢幾份 | 備貨 − 賣出 |
| `missed` | 賣完之後，還有幾位客人想買卻沒買到 | 客人卡片上「賣完了」的數量 |
| `status` | `ok` 正常、`out` 缺貨、`over` 報廢過多 | 規則書「倉庫盤點」 |
| `suggest` | 明天建議備幾份 | 賣出 ＋ 沒買到 |

## 步驟

1. 執行上面的指令，讀每一天的 `inventory`
2. 先驗算：`waste` 有沒有等於 `stocked − sold`？對不上就停下來回報，**不要用錯的資料做建議**
3. 挑出 `status` 不是 `ok` 的菜
4. ★ 建議備貨量要不要再調整（例如：明天客人比較多的日子，要不要多備幾份？多備幾份？）：
   - 只對通過驗算的缺貨或報廢過多品項提調整。先列「基礎建議＝賣出＋賣完後沒買到」，再列「與原備貨的差額＝基礎建議－原備貨」。用沒買到人數說明可能少賣的份數，用「報廢份數 × 規則書單份成本」說明浪費的備貨成本。
   - 同一可比期間內，以「各品項賣出量 ÷ 全部品項賣出量」看銷售佔比，以「各品項賣出量 ÷ 各品項備貨量」看售出率，作為周轉速度的參考。依兩項數字的相對表現說明 A 類主力、B 類配角、C 類長尾的分級理由。優先看 A 類缺貨與 C 類報廢率（報廢量 ÷ 備貨量）。分母為 0 或資料不足時，註明無法計算或分級。ABC 分級只決定檢視順序。
   - 另列「隔日條件後的調整」。有平日／假日、天氣或活動資料時，說明隔日與哪些歷史盤點可比。若有同品項、相近條件的有效資料支持調整，可用該情境的「賣出＋賣完後沒買到」估算，並列出與基礎建議的差額和算式。只有預告或沒有量化證據時，沿用基礎建議並說明原因。
5. ★ 同一樣菜連續幾天都缺貨或報廢過多，要怎麼提醒：
   - 同一道菜在連續至少兩個營業日都缺貨，或都報廢過多，標明「持續缺貨」或「持續報廢過多」，逐日列出日期或天數、備貨、賣出、沒買到和報廢。只有一天、日期有缺口或中間有無效資料時，只描述可核對的日期。
6. 用下面的回報格式回報

## 回報格式

```text
策略檔：
驗算結果：通過 / 第 N 天的 ○○ 對不上（寫出哪個數字）
第 N 天：
  缺貨：菜名 備 … 賣 … 沒買到 … → 建議 …
  報廢過多：菜名 備 … 賣 … 報廢 … → 建議 …
★ 建議備貨成本：菜名、採用的建議份數 × 規則書單份成本 ＝ 金額。
  完整策略可執行性：列出所有預定上架餐點（含備貨量原樣採用的餐點），核對上架最多 4 樣、各品項份數為非負整數、總份數最多 80 份，以及各品項定價在規則書的整數範圍內。
  列出總份數算式與各品項備貨成本加總。核對宣傳費為 0、200 或 500 元，且總備貨成本＋宣傳費不超過可用資金。缺少任何必要資料時，填「尚無法確認可執行性」。
下一版每天建議的備貨量：
```

## 寫完檢查

- [ ] 每一個數字都能在盤點資料裡找到
- [ ] ★ 篩選和計算前，逐筆核對天數、菜名與各欄位是否齊全。備貨、賣出、報廢、沒買到、建議量都是非負整數，且賣出不超過備貨、報廢＝備貨－賣出。有沒買到的人時，確認該菜確實已賣完。
  - 有人因賣完沒買到就是缺貨。其餘報廢達 5 份為報廢過多，其他為正常。核對狀態和建議量（賣出＋沒買到），包含畫面標籤與試算代碼的對應。
  - 遇到缺漏或矛盾，回報第幾天、哪道菜、哪個欄位，以及讀到的值和應有的值（可算時）。停止對該筆提出建議，其餘驗算通過的資料才可分析。
  - 標明每個原始數字的來源，只用使用者提供的盤點資料、模板列出的來源，以及規則書中的成本與門檻。每個衍生數字都列算式。
